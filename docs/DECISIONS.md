# Cyberine DevGuard design record

The plugin is a Claude Code port of a personal cross-repo write guard: a PreToolUse hook that stops a session from writing files outside its own repository and the directories the session was allowed. Harness facts cited as `F<n>` were measured on Claude Code 2.1.283 with the probe scripts in `tests/live/`.

## Name

- Name `cyberine-devguard`, display name `Cyberine DevGuard` (plugin and marketplace, skill namespace `/cyberine-devguard:*`, repo config `.claude/cyberine-devguard.json`). Repository `cyberinecore/cc-dev-guard`. The entry script stays `scripts/devguard.mjs` and internal verdict codes keep `devguard-*`; neither is shown in the listing. Measured output quoted in `docs/LIVE-MATRIX.md`, `docs/FAILURE-MODES.md` and `docs/PARITY.md` predates the rename and shows the old `devguard` prefix.
- Collision check, 2026-09-28: npm `devguard` is taken (an MCP dev-diary server, 0.5.0). GitHub `devguard` is an OWASP-listed supply-chain security project (`l3montree-dev/devguard`, 163 stars, with `devguard-action` and a VS Code extension), so the name is likely to hit the directory's "Name matches a known brand" reviewer hold and confuses users in the same security space. Alternatives checked the same day, all with a same-named or near-named project: `repofence` (npm package taken), `scopefence` (a GitHub repo "Repo fences for coding agents"), `writefence` (a GitHub project about agent memory writes), `scopeguard` (a Rust crate with 567 stars), `lanekeeper` (unrelated small repos, npm free), `repo-scope-guard` (npm free, generic words).
- Status: settled by the owner on 2026-09-28. The owner prefix `Cyberine` separates the listing from OWASP DevGuard, which is a different product (supply-chain vulnerability management), while keeping the working name; a reviewer may still read the shared `DevGuard` part as a brand match, and `repotether` stays the fallback if the listing is held.

| D14 | Paths are compared after `realpathSync.native` on the existing part, which canonicalizes symlinks and, on case-insensitive volumes, case; the not-yet-existing tail is compared as written, so a variant spelling there is a false ask, never a false pass. | settled |
| D15 | Writes to Claude Code settings files (`.claude/settings.json`, `.claude/settings.local.json`, the config dir's settings files) and to session transcripts always ask, because each can widen scope (additionalDirectories, env, a forged snapshot). devguard option keys set by the session repo's committed `.claude/settings.json` env are applied tighten-only. Project env that hides `node` or preloads code (`PATH`, `NODE_OPTIONS`) is outside what a hook can defend; it is Claude Code's workspace-trust boundary and the README says so (`docs/SECURITY-REVIEW.md` rows 13-16). | settled |
| D16 | Every git call runs with `GIT_*` variables removed and `-c core.fsmonitor=false`, because `git check-ignore` and `git rev-parse` run a target repo's fsmonitor command otherwise. A directory git cannot read but that holds a `.git` entry counts as a repository. | settled |
| D17 | Supersedes D6 as the default grant source, because the Anthropic Software Directory Policy says software "must not query or extract data from Claude's memory, chat history, conversation summaries". Default: allowed dirs come from `permissions.additionalDirectories` in managed, user, project and local settings, from `DirectoryAdded` hook events recorded per session in the plugin data dir, and from the `--add-dir` arguments of the `claude` process (`CLAUDE_PID`; `/proc/<pid>/cmdline`, else `ps`). The transcript snapshot (D6) is opt-in through `read_transcript` and falls back to these sources when unreadable. Cost: without the transcript, a directory removed mid-session stays allowed until the session ends, and `--add-dir` paths with spaces are missed on macOS. Writes into devguard's data dir always ask, because the `/add-dir` records there are a grant. | settled (measured: `docs/LIVE-MATRIX.md` rows add-dir, settings) |

| D25 | Amends D7: Bash is matched for one shape only, `git worktree add`, because stray worktrees are a measured failure (a public report counted 45 extra worktrees, 36 pointing at deleted `/tmp` folders) and the shape is narrow enough to parse. A path passes only when it lies directly under the main repository's `.claude/worktrees/` and not inside an existing linked worktree there (nested worktrees, incident 2026-05-24 in the Go hook's history). Anything else, including a path or `-C` built from a variable, `--git-dir` or `--work-tree`, asks (deny under bypassPermissions), never denies outright, to match every other devguard answer. The parser follows quotes, `-C`, `cd` within the same command and subshell scopes; it is a guardrail, not a boundary, and the README says so. Option `worktree_guard` (default true) turns it off; a repository can only turn it on. A Bash command without the word `worktree` returns before any config read or git call; measured cost 35 ms per Bash call against 24 ms for a bare node start. | settled (measured: `docs/LIVE-MATRIX.md`, worktree rows) |
| D26 | Worktree placement ships as a second plugin, `cyberine-worktree`, in the same marketplace, not as a devguard option, because a `WorktreeCreate` hook cannot hand creation back to Claude Code: on 2.1.287 an empty stdout fails ("hook succeeded but returned no worktree path") and `{"hookSpecificOutput":{"hookEventName":"WorktreeCreate"}}` without `worktreePath` fails validation ("expected string, received undefined"), contrary to the type comment. A hook listed in devguard's static `hooks.json` would therefore replace native creation for every user. Installing the plugin is the opt-in. Behaviour matches the owner's Go hook: path `<main root>/.claude/worktrees/<name>`, branch `worktree/<name>`, `git -C <cwd> worktree add --no-track -B <branch> <path> HEAD`, main root through git-dir versus common-dir and the first `git worktree list` entry re-resolved through `--git-dir` (absorbed submodules), no climb to a superproject, idempotent when `<path>/.git` exists, only the path on stdout. Input is `name` and `cwd` (measured; no `worktree_path` or `git_ref`, both read defensively when present). Names with a segment other than letters, digits, `.`, `_`, `-` are refused. The plugin is self-contained (node builtins only) because each plugin is installed from its own directory. | settled (measured: `docs/LIVE-MATRIX.md`, worktree rows; parity 5/5 against the Go hook) |
| D27 | The worktree report changes nothing: it prints `git worktree prune` and `git worktree remove` for the user to run. Merged branches come from `gh pr view` because ancestry misses squash merges; `gh` runs under the user's active account with a fixed list of variables (no token variable is read), and one failure per repository stops further `gh` calls there and prints one line. The ancestry fallback is labelled "merged or empty", since a fresh branch with no commits is also contained in the default branch. | settled |
| D28 | Amends D7 and D25: with `bash_guard` (default true) every Bash command is parsed for obvious write shapes (redirects, `tee`, `sed -i`, `dd of=`, `cp`/`mv`/`install`/`ln`/`rsync` destinations, `touch`/`mkdir`/`rm`/`rmdir`/`truncate`, and git subcommands that change a repository under `-C` or a `cd`), and each target goes through the same `decide()` as a file-tool write, so allowances, ignored paths, the always-ask list and the bypass deny apply unchanged. Directory targets are judged as a path inside the directory, because the repository of a directory is decided by the directory itself, not its parent. Heredoc bodies are skipped, a fd number before `>` is not a word, and a target built from a variable is skipped rather than asked about: a prompt on every `> $OUT` would teach users to approve without reading. Best effort, stated in the README; a repository file can only turn it on. | settled (measured: `docs/LIVE-MATRIX.md`, Bash rows) |
| D29 | Write tools of the reference filesystem MCP server are judged like file-tool writes: matcher `mcp__.*__(write_file|edit_file|create_directory|move_file)`, and a call is taken only when its input matches that server's documented schema (`write_file` path+content, `edit_file` path+edits, not `dryRun`, `create_directory` exactly path, `move_file` source+destination; README of `modelcontextprotocol/servers/src/filesystem`, read 2026-10-03). The tool name alone is not provenance: the hook input names the server only by its configured name. `move_file` judges both paths, since moving a file out of another repository changes it. Other servers stay out of scope. | settled (measured: `docs/LIVE-MATRIX.md`, MCP rows) |
| D30 | Amends D12: option `isolate_worktrees` (default false) makes a session rooted in a linked worktree treat the main checkout and the other worktrees of its repository as outside its scope (reason "other-worktree"); the usual allowances, ignored paths and allowed directories still pass. Default off because writing from a worktree back to the main checkout is a normal workflow. A session in the main checkout is not affected. A repository file can turn it on, not off. | settled (measured: `docs/LIVE-MATRIX.md`, isolate rows) |
| D31 | Every cross-repository ask and deny reason names the fix with the target's directory: `/add-dir <dir>` for this session and the `extra_allowed_dirs` option for every session, plus the note that a path the other repository gitignores passes. Reading the user's prompt for an allow word was rejected: the directory policy forbids reading chat, and the model could grant itself. | settled |
| D32 | `cyberine-worktree` 0.2.0 adds a SessionStart hook that reads `hooks.WorktreeCreate` from the user and project settings files and prints a `systemMessage` when another entry exists, because every `WorktreeCreate` hook runs in parallel and a diverging one leaves an orphan worktree. | D33 | Multi-plugin layout, checked 2026-10-03 against `code.claude.com/docs/en/plugin-marketplaces`, `code.claude.com/docs/en/plugins/publish` and `claude.com/docs/plugins/submit`. A marketplace may list several plugins; a relative `source` such as `./plugins/cyberine-worktree` is the documented form for a plugin inside the marketplace directory; a plugin in its own repository uses `{ "source": "github", "repo": "owner/repo" }`, and one in a subfolder of another repository `{ "source": "git-subdir", "url": "owner/repo", "path": "..." }`. For the directory, "each plugin folder is its own submission", with an optional plugin path, and "the directory reads and scans only that folder". So devguard keeps its submission at the repository root, which also contains `plugins/cyberine-worktree/` and is scanned with it, and cyberine-worktree can be listed as a second submission with path `plugins/cyberine-worktree`. | D34 | Option `danger_guard` (default true) denies data-destroying Bash commands in every permission mode and regardless of `mode`, ported from the Go `bash-guard` (`nf-hooks bash-guard`) with every case of its table tests passing (`tests/fixtures/bashguard-cases.mjs`, `docs/PARITY.md`). Deny, not ask, because under bypassPermissions a hook is the only gate left and an ask there passes for some paths (D2). It runs before the write-shape check of D28 and does not depend on `bash_guard`. The Go hook's personal parts became options: `protected_branches` (the Go list as default), `deny_aws_s3_deletes` (default true) and `allow_danger_env` (a second escape variable name, so `NF_ALLOW_DANGER` keeps working where the user sets it). The escape is `CY_ALLOW_DANGER=1` in the hook's environment; a value the session repository's `.claude/settings.json` or `.claude/settings.local.json` env block sets is ignored, because Claude Code passes that block to hooks and D4 forbids a repository from loosening the guard. A repository file can set `dangerGuard` and `denyAwsS3Deletes` to true and add `protectedBranches`; `allowDangerEnv` from it is ignored. A failure to load the engine already answers ask (deny under bypassPermissions) for every Bash call, which is the visible signal; node missing fails open and is surfaced by SessionStart (`docs/FAILURE-MODES.md`). | settled (unit and live parity) |
| D35 | Amends D2: under bypassPermissions a cross-repository or other-worktree verdict in `ask` mode is rendered as `deny-once` (deny the first write per session and repository with "Retry only if the user explicitly names that target this turn", pass a retry within 10 minutes), not a hard deny, because the owner wants to keep asking Claude in chat for a cross-repository change in a bypass session, and D2's reason (an ask passes there for some paths) is met by never answering ask. Option `bypass_strict` (default false) keeps the hard deny; a repository file or settings env can only turn it on. Trade-off accepted: in bypass the model decides whether the user asked, as with the Go hook's deny-once. | settled (unit; live: `docs/LIVE-MATRIX.md`) |
| D36 | Amends D4: a cross-repository target passes (`ignored-nested-repo`) when its repository's top level lies strictly inside the session repository's top level and the session repository's `git check-ignore` reports that top level ignored, under option `allow_ignored_nested_repos` (default true). Reported 2026-10-03: `git add`/`commit` in an agent's scratch repository under a worktree's `.local/tmp/` was asked about (denied under bypass). | D37 | Amends D34: danger_guard diverges from the Go table in three text-only cases, because they denied harmless commands every session (task km5zk, measured on 0.6.0 in this repository's own sessions). A heredoc body is not scanned only when all of these hold: the command receiving it is `cat` or `tee` (not `awk`, which can execute it), and when the heredoc sits inside `$(...)` the command around that substitution is `git` (so `bash -c "$(cat <<'EOF' ...)"`, `ssh`, `eval` or `psql -c` around it keep the scan), the `<<` is outside quotes and is not a `<<<` here-string, the line has no pipe after it, no process substitution and no trailing `\`, it is the line's only heredoc, the closing delimiter is found, and an unquoted delimiter's body holds no `$(` or backtick (which the shell would run). So `cat > seed.sql <<'EOF'` or a `git commit -m "$(cat <<'EOF' ...)"` message passes, and anything else keeps the old scan. TRUNCATE is denied in any case when followed by a table name (`truncate users;`, `TRUNCATE TABLE x`, `truncate a, b`, `truncate t1,t2`, a name followed by `/*`, `--` or Postgres's `*` descendant marker); a Tailwind class (`truncate text-sm`) passes because the next word continues with a single `-`, which no unquoted table name does. DROP DATABASE/SCHEMA/TABLE is unchanged, a prefix match that also covers `DROP TABLESPACE`. `rm -rf "$(mktemp ...)"` passes only when the whole argument is that one substitution holding nothing but `mktemp`, its flags and a template; anything appended (`/*`, `/..`) or any other command inside it is denied as before. Three adversarial review rounds on 2026-10-04 found 31 bypasses in looser drafts, all now in `DEVGUARD_DENIES`: Codex (gpt-6.1-sol) found 11, among them `psql <<'SQL'` with a lowercase `truncate users;`, `sudo psql -c 'truncate users'`, `awk '{system($0)}' <<'EOF'`, a quoted `'<<EOF'` hiding the next line and `rm -rf "$(mktemp -d /missing/XXXXXX)"/*` (empty output, so `/*`); Muse (muse-spark-1.3) found 13 more, among them `bash -c "$(cat <<'EOF' ...)"`, `truncate a, b` and `DROP TABLESPACE`, then 7 sharing one cause, `TRUNCATE users*`. A second Codex round was refused by the provider's cybersecurity filter, so rounds two and three ran on Muse. Kept on purpose: a quoted command handed to `tmux send-keys` is still denied, since the pane runs it like `ssh` would, and an `rm -rf` target built from another substitution or variable is still denied. Every Go table case keeps its verdict (`tests/dangerguard.test.mjs`); the divergences are `DEVGUARD_ALLOWS` and `DEVGUARD_DENIES` in `tests/fixtures/bashguard-cases.mjs` and are listed in `docs/PARITY.md`. | settled (unit) |
| D24 | Amends D5: `autoMemoryDirectory` is also accepted from the session repo's `.claude/settings.local.json`, but only while git reports that file ignored (`git check-ignore`, which never reports a tracked file). An ignored local settings file is the user's own file, not something a cloned repository ships, and Claude Code itself reads the key from trusted local settings (F18); a tracked or unignored `settings.local.json` and the project `.claude/settings.json` stay untrusted.
